## Финальный эксперимент — генератор правил (22.09.2026)

**Метод.** Знание о типовых поломках ответа лежит в коде списком проблем
(`PROBLEMS_GENERAL` / `PROBLEMS_SPECIFIC`, по 17 записей: симптом / почему
ломает проверку / что делать вместо). Формулировки правил пишет LLM; готового
текста правил в репозитории нет. Блок дописывается к системному промпту солвера
после сборки индекса, первая фраза промпта (контракт `<code>`) не трогается.
Синтетику в базу знаний больше не генерируем — доставка только через промпт.

**Пять конфигов** (`final_test_configs/`, отличие ровно в системном промпте):
`c0_base` (правил нет), `c1_general_per_problem`, `c2_general_batch`,
`c3_specific_per_problem`, `c4_specific_batch`. Два списка проблем: `general`
(свойства класса задач, без артефактов бенчмарка) и `specific` (те же 17 с
конкретикой). Два режима: `per_problem` (вызов на проблему, принятые правила
подаются дальше, повтор снимается ответом `COVERED`) и `batch` (один вызов,
модель сама объединяет родственные, не больше `n_rules`).

**Кластер.** Новый, Alibaba PPU, узел ali117197, лаборатория prims (4 карты,
две заняты постоянными сервисами коллеги, две свободны). Солвер и генератор
правил — одна модель `Qwen3.6-35B-A3B` из `$MODELS_ROOT`, поднимаем сами на
порту 30000. Эмбеддер не поднимаем: берём работающий сервис лаборатории на
7216 (`Qwen/Qwen3-Embedding-4B`). Режим рассуждений выключен
(`enable_thinking: False`) — ответ солвера разбирается как голый код. Модель
поднимается под именем, равным пути к весам: солвер грузит токенайзер по
идентификатору, который вернул эндпоинт.

**Порядок.** Пять прогонов последовательно, с `--log-chunks`, без смоука.
Правила пишутся на этапе сборки пайплайна; посмотреть их отдельно, несколькими
seed, можно через `db_scripts/write_rules.py`. В папке каждого прогона лежит
`system_prompt_used.txt`; дампы генерации — `results/gen_dumps/rules_*.jsonl`,
при `rebuild: False` повторный прогон идёт на том же тексте побайтно.

## exp15 — ПРОГНАН И РАЗОБРАН (24.08.2026)

Три конфига с `--log-chunks`. Ручная база воспроизвелась, обе версии
автоматического метода стоят на месте.

### Что показал лог ретрива

**1. Гипотеза «сген. инструкции не ретривятся» ОПРОВЕРГНУТА.** Сген. доки
доезжают до контекста ЧАЩЕ ручных: 74% задач против 58% (gen_instruct),
27.8% всех чанков против 16.9%. gen_api — 46% задач, 14.3% чанков.
Проблема не в доставке, а в содержимом.
NB: у сген. доков `doc_id` строкой, у корпусных int — фильтр по int даёт
ложный ноль попаданий.

**2. Механика ретрива.** `QdrantAdapter.search` — гибрид dense+sparse со
слиянием RRF, `prefetch limit=top_k` у каждого канала. Отсюда скоры
0.5/0.333/0.25 = 1/(rank+2): 5 слотов делятся между каналами (~3 dense +
~2 sparse). В ОБА канала одновременно попадают 16% ручных чанков против
6%/3% сген. — ручные совпадают и семантически, и лексически, сген. лезут
одним каналом.

**3. Проигрыш — от отсутствия контента, не от «отравления».** Флипы против
pure_aug: gen_api 50 выиграл / 151 потерял, gen_instruct 67/160. Среди
потерянных 94% (gen_api) и 88% (gen_instruct) имели ручной док в контексте
pure_aug при базовой ставке 58%; доля сген. доков на потерянных задачах =
базовой.

**4. Спам-аттракторы и дыры покрытия.** gen_instruct: один док в 205
контекстах (15% попаданий), top-5 доков = 36%, НЕ ретривнулись 102 из 241.
gen_api: top-1 = 101 задача, top-5 = 46%, не ретривнулись 74 из 148.
Ручная: top-1 = 57 (7%), top-5 = 23%, не ретривнулись 30 из 197 (21 из них
`migr_`).

**5. Баг переписи API в ApiGuideGenerator** (проверено локальным прогоном
ценза без LLM). `_METH_RE` (`api_guides.py:44`) ловит хвост
квалифицированного вызова: в `np.arange(` видит `.arange(` и приписывает
его библиотеке ДОКУМЕНТА. 41 326 из 87 341 совпадений (47%) мусорные;
70 из 149 отобранных API — голые методы, 39 из них принадлежат другой
библиотеке: (scipy, .plot) 1065, (scipy, .array) 773, (matplotlib,
.arange) 384, (pandas, .randn) 233. Итог в дампе — док «How do I use the
numpy method .plot()», попавший в 89 контекстов. Дедуп `qual_tails`
(`api_guides.py:157`) работает только внутри библиотеки. Плюс перекос
квот: tensorflow 37 доков, pandas 20, sklearn 3.

**6. Фон (ограничение пайплайна, не метода).** 25–30% ретривнутых
КОРПУСНЫХ чанков — из чужой библиотеки (380 задач из 1000 имеют ≥2 таких);
~5% пар чанков в контексте — почти дубликаты. Полтора-два слота из пяти
уходят в мусор при любом методе генерации.

### Формализация: требования к генерируемому доку (S1–S8)

- **S1.** Жанры неравноценны: протокол (`guide_`) — единственный сильный
  класс; рецепт (`howto_`) ~0 в среднем, но держит хвост редких задач;
  миграция при слепом семантическом ретриве ВРЕДНА (−17 пп): якорится на
  текст ошибки, которого в запросе нет.
- **S2. Протокольный док:** утвердительный заголовок (не вопрос);
  называет три факта — сетап уже выполнен в том же namespace, реальные
  значения скрыты и отличаются от показанных, ответ идёт в запрошенную
  переменную; код ≤3 строк, БЕЗ `import` и БЕЗ литеральных датасетов;
  переменные из типового набора (a, arr, df, s, x, y, X, ax, t, model);
  контрпример перечислением, а не вторым скриптом. Нужен общий вариант +
  по одному узкому на библиотеку (оба в топе попаданий: 57 и 56 задач).
- **S3. Рецепт:** заголовок-вопрос; тело различает ДВЕ похожие дороги;
  код 2–5 строк на готовых переменных, размеры из данных; целевой API
  редкий (частота по корпусу 5…100).
- **S4.** Один док = одна ловушка, без клонов. Источник клонов у `fmt_` —
  шаблон «angle × 7 библиотек × варианты» (`rag_guides.py:265`).
- **S5.** Частота API в корпусе — рабочий критерий отбора темы: то, что
  встречается 400+ раз, модель и так знает.
- **S6.** Пример в доке демонстрирует ПРОТОКОЛ, а не самостоятельный
  скрипт. Сейчас промпты требуют обратного дословно — «with your own tiny
  invented data» (`api_guides.py:184`, `rag_guides.py:367`).
- **S7.** Обязательный `result = ...` снять: он даёт `result = plt`,
  `result = plt.show()` в 99–100% сген. доков.
- **S8.** Самый ценный класс доставляется хуже всех: `guide_` доезжают до
  155 задач из 1000 и почти всегда одним каналом ретрива (в обоих каналах
  2% попаданий против 21% у `howto_`) → аргумент за зарезервированный слот.

## exp17 — что было спроектировано и реализовано (справка)

**Шаг 1. Материализация сген. корпуса в .db (этап пайплайна).** Стадия
сборки корпуса (загрузка → документный фильтр → генерация →
материализация) выносится в общую функцию, вызывается из `SimplePipeline`
(основной шаблон, все конфиги с exp12 — `type: SIMPLE`) и из
`SimplePipelineWithDocFilter`. Копия исходной .db под новым именем, INSERT
сген. доков с int-id и секцией `generated_<method>`, таблицы
`generation_meta` (метод, модель, эндпоинт, seed, класс, пункт плана, хеш
промпта) и `plans` (сырой план). Материализация после всех документных
операций и до чанкинга → файл равен проиндексированному корпусу и годится
для pure-повтора. Чанковый фильтр в .db не отражается — фиксировать в
runtime_stats. Параметры: `document_filter_stage: pre_generation |
post_generation`, `on_exists: rebuild|reuse|fail` (дефолт rebuild —
иначе повторится vector-db-reuse bug), `seed`. Seed раздаётся ПО ЗАДАНИЯМ
(base_seed + index), порядок заданий детерминированный, `sorted()` вместо
итерации по set (PYTHONHASHSEED). Фильтрация опциональна: все четыре
комбинации (±фильтр × ±генератор) должны работать; без генератора копия не
создаётся. Файлы — `data/generated/`, в .gitignore.

**Шаг 2. Планирующий генератор.** Стадия 1: LLM получает материал корпуса
(Notes/Warning/See Also, пары похожих API, неочевидные дефолты сигнатур,
deprecated-фразы, API частоты 5…100 из ПОЧИНЕННОЙ переписи) и выдаёт план
построчным JSONL: class / lib / trap / api / vars. Планирование пачками,
в каждый следующий вызов — список уже принятых заголовков. Стадия 2: по
одному доку на пункт, разделитель-сентинел (JSON ломается на коде).
Температуры: план 0.8, доки 0.2. Ручка `plan: on|off` для абляции.
Контроль исполнения плана: стабильный id пункта; дедуп на уровне плана
(заголовок + эмбеддинг, порог ~0.85, сверка с принятыми и с заголовками
корпуса) и повторный дедуп готовых доков; проверка соответствия дока
пункту (API-токен, библиотека, класс) с одним повтором; финальный статус
каждого пункта (generated / duplicate / rejected:<правило> / parse_failed
/ retry_exhausted) и отчёт покрытия плана в лог И в БД.

**Шаг 3. ApiGuideGenerator чиним целиком (вариант B, решение Konstantin).**
Регекс не засчитывает совпадения внутри span квалифицированного вызова;
владелец метода определяется глобально, а не по библиотеке документа;
дедуп имён между библиотеками. Критерий отбора меняется с топ-частоты на
редкие/спорные API (S5). Промпт переписывается под контракт S2/S3/S6/S7.
Гоняется отдельным конфигом — это абляция «плоский API-якорь» против
«планирование». Контракт документа и протокольный блок у обоих методов
ОБЩИЕ, иначе сравнение не про отбор тем.

**Шаг 4. Зарезервированный слот — ОТЛОЖЕН** (решение Konstantin 24.08.2026,
в exp17 не входит). Дизайн на будущее: отдельный `ICLBlock` (интерфейс

### Два молчаливых no-op, найденных при написании exp17 (24.08.2026)

**1. Генерация была бы пустой.** Коммит b1af9ba («prompt optimization»)
перевёл `RagGuideGenerator._chat` на `self.prompt(...)`, но не добавил классу
миксин `PromptDiscoverable`. Каждый вызов LLM падал бы с AttributeError, а
`_run_jobs` глушит исключения в счётчик — генератор молча вернул бы 0 доков.
exp15 гонялся на коммите 5d56cbd (до этого), поэтому не пострадал; exp17
пострадал бы полностью. Починено (`class RagGuideGenerator(PromptDiscoverable,
Generator)`), проверено: вызов доходит до сети.

**2. QUERY_GENERATOR никогда не работал.** В конфигах exp13/14/15 компонент
объявлен ключом `enchancer`, а параметр пайплайна называется `enhancer`.
Фабрика подставляет зависимости по имени параметра, так что компонент
строился и выбрасывался. Доказательство в самих результатах: `eval_llm_calls`
= 1000 при 1000 задач во ВСЕХ трёх конфигах exp15, то есть ровно один вызов
солвера на задачу и ни одного вызова энхансера.

Следствие для разбора exp15: запрос к ретриверу — это сырой текст задачи,
одинаковый во всех конфигах. Значит оговорка «часть расхождения ретрива —
шум LLM-запросов» НЕВЕРНА, её снимаем: расхождение корпусных чанков между
конфигами (26% у gen_instruct, 14% у gen_api) — это чистое ВЫТЕСНЕНИЕ
сгенерированными доками. В exp17 энхансер сознательно не объявляется: чинить
его сейчас значило бы менять пайплайн посреди сравнения.

## exp17 — ПРОГНАН И РАЗОБРАН (25.08.2026)

Четыре конфига на ПОЛНОЙ Qwen2.5-32B-Instruct. Итог: **генерация не сработала
снова, но по новой причине**, и причина измерена.

| Конфиг | PASS@1 | сген. доков | ретрив сген. доков |
|---|---|---|---|
| `pure_e17` (бейзлайн) | 0.445 | — | — |
| `gen_plan_e17` | 0.441 | 86 | 2.1% чанков, 5 доков из 86 |
| `gen_noplan_e17` | 0.443 | 98 | 0.8% чанков, 14 из 98 |
| `gen_api_e17` | 0.450 | 119 | 1.4% чанков, 19 из 119 |

Разброс 0.9 пп при шумовом поле ~1.4 пп — различий нет. Флипы задач:
gen_plan −4, gen_noplan −2, gen_api +5. Бейзлайн 0.445 согласуется с exp8
(0.449 на той же полной 32B) — опорная точка получена, она и была главной
пользой конфига 1.

### Главная причина: отбор по редкости увёл корпус в экзотику

Мы попали в целевую метрику специфичности идеально (медианная частота API в
корпусе: 32 / 45 / 25 против 31 у ручных рецептов) — и промахнулись мимо
задач. Измерено:

| набор | доля доков, чей API вообще встречается в текстах DS1000 | TF-IDF: задач с близким доком (>0.25) |
|---|---|---|
| ручные `howto_` | 71% | 238 |
| exp15 gen_instruct | 94% | 297 |
| **exp17 gen_plan / noplan / api** | **39% / 41% / 45%** | **9 / 36 / 57** |

Ошибка в рассуждении: у ручных рецептов медиана частоты API = 31, но это
медиана по СМЕСИ — 75-й перцентиль 104, максимум 2770. Ручной док опирается
на обычный глагол (`.reshape`, `.groupby`, `np.argsort`, `pd.concat`) и
различает ловушку внутри него; редкий токен там присутствует как деталь. Мы
же сделали редкость ПЕРВИЧНЫМ критерием и получили `tf.distribute.ReduceOp.SUM`,
`tf.keras.metrics.Mean`, `.getnnz`, `scipy.stats.moment`, `torch.diagonal`.

Проверка исправления на данных (отбор ничего не знает о DS1000, замер —
постфактум, как и весь анализ):

| правило отбора | отобрано | доля API, встречающихся в задачах |
|---|---|---|
| как в exp17: редкость 5..100 | 126 | **21%** |
| средняя полоса 100..500 | 91 | 48% |
| голова ≥200 + требование спутываемости | 48 | **62%** |
| голова ≥100 + требование спутываемости | 69 | 52% |
| (для сравнения: ручные рецепты) | 249 API | 52% |

### Что ещё видно в материализованных .db

- **Бюджет ушёл не туда.** tensorflow получил 24-30 доков на 45 задач
  бенчмарка, sklearn — 2-3 дока на 115 задач. Квоты считались от размера
  корпуса, а корпус перекошен (tensorflow: 4887 доков, 20 294 примера).
- **Модель обошла контракт.** 79-108 доков из 86-119 содержат блок
  «WRONG», у 3-6 из них импорт спрятан именно туда. Запрет импорта в
  рекомендованном коде превратился в шаблон «WRONG/RECOMMENDED», а не в
  протокольный стиль ручных доков.
- **Фактические ошибки на редких API.** `scipy.stats.moment`: «первый
  момент — это среднее» (неверно, первый центральный момент = 0);
  `torch .parameters()`: «вызывает deprecation warnings» (выдумано). Прямое
  следствие отбора по редкости: модель хуже знает такие API и сочиняет.
- **Выход просел.** 150 заданий → 86 / 98 / 119 доков; 23-56 заданий сгорели
  в `retry_exhausted`, доминирующая причина отбраковки —
  `import_in_recommended_code` (109-181 срабатываний). Отбракованные черновики
  никуда не пишутся — аудировать их нечем.
- **Протокольный класс сгенерирован хуже всех.** Из 24 заданий выжило 12-16,
  и только 2-3 дока называют все три факта (сетап выполнен / значения скрыты /
  переменная ответа). Это самый ценный класс по exp15, и он самый слабый.

### Что из механики сработало

Материализация корпуса, seed, провенанс и отчёт покрытия отработали штатно:
все три .db читаются, `generation_meta` и `generation_plans` заполнены,
статусы пунктов плана видны, `corpus_build` в runtime_stats заполнен. Именно
это позволило за один проход установить причину, а не гадать. Планирование
дедуплицировало 22 смысловых дубля из 161 пункта; клонов на выходе нет
(в exp15 один док сидел в 205 контекстах — здесь такого нет).

### План следующего шага (не начат, обсуждается)

1. Перевернуть отбор: якорь — частотный API (≥100-200 по корпусу) плюс
   ОБЯЗАТЕЛЬНЫЙ признак спутываемости (look-alike сосед / нетривиальный
   дефолт / депрекейшн). Улику «API X встречается N раз» убрать вовсе — она
   не несёт ловушки.
2. Квоты по библиотекам не от размера корпуса. Равные доли — честный
   безбенчмарочный дефолт.
3. Не отбраковывать док целиком из-за импорта — вырезать импорт из
   рекомендованного блока и валидировать повторно; отбракованные черновики
   дампить.
4. Закрыть лазейку «WRONG-блок»: запрет импорта распространить на весь
   документ, а не только на рекомендованный блок.
5. Протокольный класс не генерировать свободно: это фиксированный небольшой набор,
   ему нужен жёсткий шаблон с тремя фактами.

## exp18 — что было изменено перед прогоном (справка)

Пять изменений, каждое отвечает на измеренную причину провала exp17.

### 1. Отбор тем перевёрнут

Было: редкий хвост 5..100 вхождений по корпусу. Стало: голова (≥100) плюс
ОБЯЗАТЕЛЬНЫЙ признак спутываемости — соседнее имя со схожим корнем, дефолт
аргумента, меняющий результат, или депрекейшн. Улика «API X встречается N раз»
удалена совсем: в exp17 она составляла 2119 сигналов из ~2800 и не несла
никакой ловушки.

Замер до прогона на итоговой конфигурации (152 темы, квоты по библиотекам):
доля отобранных API, встречающихся в текстах задач, 21% → 49% (у ручных
рецептов 52%). Медианная частота отобранного API 186 против 25-32 в exp17,
минимальная 20 — ниже пола не опускаемся даже ради равных квот, поэтому
sklearn получает 10 тем вместо 21: у него в корпусе просто нет частотной
головы.

Разбор ошибки: медиана частоты API у ручных рецептов = 31, но это медиана по
СМЕСИ — 75-й перцентиль 104, максимум 2770. Ручной док опирается на
повседневную операцию и кладёт ловушку внутрь неё; редкий токен — деталь
решения, а не тема.

### 2. Контракт документа: ноль контрпримеров

`- if you show a wrong way, put it in a separate block ... with the word WRONG`
из контракта удалено — именно эта строка породила 0.87–0.92 блока «WRONG» на
документ (у ручных рецептов 0.01). Теперь: ровно ОДИН блок кода, и он
правильный; чего делать нельзя — одним предложением прозы. Импорт и построение
данных из литералов запрещены во всём документе, а не только в рекомендованном
блоке.

Основание — не вкус: два контрпримера exp17 оказались галлюцинациями,
попавшими в базу исполнимым кодом (`scipy.special.ccdf` не существует;
«первый момент — это среднее» неверно, проверено в venv).

### 3. Форма показывается, а не описывается

В каждый промпт кладутся 3 документа из ручной базы как образцы ФОРМЫ, с
ротацией по номеру задания. Отбирались механически: каждый образец сам
проходит контракт, не строит данные из литералов и работает с переменными,
которые у читателя уже есть. Документ, повторивший тему образца,
отбраковывается со статусом `copied_exemplar`.

Пороги формы откалиброваны по 85-му перцентилю ручного корпуса:
директива — 3 строки кода и 100 слов, рецепт — 4 строки и 70 слов.

### 4. Выход: починка вместо отбраковки

Импорт вырезается из кода, лишние блоки обрезаются до первого, и только потом
идёт валидация. В exp17 на правиле про импорт сгорело 23–56 заданий на конфиг.
Отбракованные черновики теперь пишутся в `*_rejects.jsonl` — раньше их нельзя
было посмотреть вообще.

### 5. Директивный класс

Углы стали разными по библиотекам: 6 общих + 6 специфичных на каждую из 7
(pandas — индекс и dtype результата, matplotlib — фигура уже создана, torch —
тензоры уже загружены, и так далее). В exp17 один и тот же текст угла шёл на
семь библиотек, отсюда 2–7 почти-дубликатных пар. Итого 48 директивных заданий
вместо 42 одинаковых. Промпт директив теперь регистрируется через
`self.prompt(...)` и попадает в `prompts.json` — раньше это был единственный
класс, чей промпт не сохранялся.

Пропорция классов смещена в пользу директив: 48 директив + ~152 рецепта из
бюджета 200 (в exp17 было 24 + 126). Основание — эффект +11.6 пп у директив
против +1.0 пп у рецептов.

   новый отбор тем. В exp17 было 0.8–2.1%, у ручной базы 16.9%.
3. Материализованные .db: профиль формы против ручной базы теми же метриками.
4. PASS@1 четырёх конфигов; вклад планирования = №2 минус №3; вклад отбора
   тем = №2 минус №4; шум = №1 против exp17 pure (0.445).

## exp18 — ПРОГНАН И РАЗОБРАН (25.08.2026)

| Конфиг | PASS@1 | доков | ретрив (доля чанков) | флипы против pure |
|---|---|---|---|---|
| `pure_e18` | 0.445 | — | — | — |
| `gen_plan_e18` | 0.447 | 169 | 1.2% | +12 / −10 |
| `gen_noplan_e18` | 0.450 | 183 | 1.5% | +13 / −8 |
| `gen_api_e18` | 0.438 | 162 | 2.0% | +11 / −18 |

Разброс 1.2 пп при шумовом поле 1.4 пп — различий нет. Контроль сработал:
`pure_e18` дал ровно 0.445, как и `pure_e17`, то есть прогонный шум по среднему
мал и метрики сравнимы между экспериментами.

### Что починилось

- **Выход**: 169 / 183 / 162 дока из 200 заданий (в exp17 было 86 / 98 / 119
  из 150). Механическая починка сработала: вырезано 14 / 38 / 5 импортов,
  лишние блоки почти не встречались (1 / 0 / 0) — правило «один блок» модель
  выполняет.
- **Контрпримеры исчезли** полностью, как и требовалось.
- **Отбор тем стал попадать в лексику задач**: 49% отобранных API встречаются в
  текстах задач против 21% в exp17 (у ручных рецептов 52%), медианная частота
  186 против 25-32.
- **Отбраковка стала видимой**: `*_rejects.jsonl` появились. Доминирует
  `prose_too_long` (52 / 58 / 166 срабатываний) — модель пишет прозы больше
  моего порога.

### Что НЕ починилось: ретрив

| | доков | ретривнулось хоть раз | доля чанков контекста |
|---|---|---|---|
| ручная v1 (exp15) | 197 | 167 (85%) | **16.9%** |
| exp17 gen_plan | 86 | 5 (6%) | 2.1% |
| exp18 gen_plan | 169 | 22 (13%) | 1.2% |
| exp18 gen_noplan | 183 | 33 (18%) | 1.5% |
| exp18 gen_api | 162 | 42 (26%) | 2.0% |

Попаданий на документ: ручные `guide_` 10.9, ручные `howto_` 4.2, наши
директивы 0.78-0.96, наши рецепты 0.16-0.48. Даже лучший наш класс в 11 раз
ниже ручного аналога.

### Причина, измеренная напрямую

| набор | символов | строк кода | API-имён на док | слов прозы | TF-IDF до задач |
|---|---|---|---|---|---|
| ручные `howto_` | 475 | **2.8** | **3.6** | 52 | **0.316** |
| ручные `guide_` | 613 | 1.6 | 2.2 | 85 | 0.172 |
| exp18 gen_plan | 478 | **1.2** | **1.7** | 62 | 0.179 |
| exp18 gen_noplan | 476 | 1.2 | 1.7 | 62 | 0.188 |
| exp18 gen_api | 487 | 1.1 | 2.3 | 66 | 0.226 |

При одинаковой длине документа у нас вдвое меньше кода и вдвое меньше
API-имён, зато больше прозы. Ретривабельная поверхность — это именно код и
имена API; проза общая и ни к чему не цепляется. Отсюда и порядок величины
разрыва.

Это следствие моих же правил: убрав контрпримеры, я одновременно поставил
потолок в 3-4 строки кода и написал «prefer fewer» — модель осела на 1.2
строки. Ручной рецепт при тех же 475 символах — это ПЛОТНАЯ идиома: 2.8 строки
кода, 3.6 API-имени, 52 слова прозы. Мы сделали ровно обратный профиль.

Косвенное подтверждение: у `gen_api` API-плотность выше всех (2.3), и у него же
лучший ретрив (2.0% чанков, 26% доков) — зависимость видна даже внутри
эксперимента.

### Что это значит для следующего шага

Порог менять надо не в сторону «короче», а в сторону «плотнее»: требовать
2-4 строки РАБОЧЕГО кода и не меньше 3 упоминаний конкретных API, а прозу
резать до ~40 слов. Целевой профиль известен точно — это ручной `howto_`.
Директивный класс при этом ретривится в 3-5 раз лучше рецептов на документ
(0.78-0.96 против 0.16-0.48), так что смещение бюджета в его сторону было
верным, но обе половины упираются в одну и ту же нехватку предметной лексики.

## Как устроены методы генерации exp18 (для справки)

Три конфига используют два класса. Ниже — что делает код, а что модель.

### PlanGuideGenerator, `plan: True` (конфиг gen_plan)

1. **Код.** Загружает 18 063 документа корпуса из sqlite.
2. **Код.** Перепись API: регексами сканирует тексты документов и 45 867
   код-примеров, считает пары (библиотека, API). Совпадения вида `.arange`
   внутри `np.arange(` не засчитываются; «голый» метод приписывается той
   библиотеке, которой имя принадлежит по всему корпусу. Итог: 9 921 API.
3. **Код.** Собирает улики трёх видов по каждой библиотеке:
   частотный API (≥100 употреблений), у которого есть похожий по имени сосед
   (40 штук); строка сигнатуры с аргументом вроде axis/inplace/keepdims
   (~876); предложение о том, что функция удалена или переименована (~191).
   Виды чередуются, не больше 240 улик на библиотеку.
4. **Модель, вызов 1 (планирование).** По каждой библиотеке пачками: на вход
   улики и список уже запланированных заголовков, на выход строки JSON
   {библиотека, тема, в чём путаница, API, переменные}. Температура 0.8.
5. **Код.** Чистит план от повторов: сначала по нормализованным словам, потом
   по эмбеддингам (порог косинуса 0.85). В exp18: 185 пунктов → 159.
6. **Код.** Собирает список заданий: 48 директивных (6 общих правил + 6 на
   каждую из 7 библиотек, тексты правил зашиты в коде) + до 152 рецептов из
   плана = 200 заданий.
7. **Модель, вызов 2 (по одному на задание).** Температура 0.2, свой seed на
   каждое задание. В запросе: кто читает документ, зачем он, тема, требования
   к форме числами, 3 примера из ручной базы, чек-лист самопроверки, формат
   ответа.
8. **Код.** Разбирает ответ, вырезает строки импорта, оставляет только первый
   блок кода, проверяет: один блок, нет импортов, нет выдуманных данных,
   лимиты длины, хотя бы одно конкретное имя, правила класса. Не прошло — до
   двух повторов с указанием причины.
9. **Код.** Убирает повторы на выходе, упаковывает документы.
10. **Код.** Копирует исходную .db, вставляет документы строками, пишет
    таблицы происхождения. Дальше пайплайн индексирует уже эту копию.

### PlanGuideGenerator, `plan: False` (конфиг gen_noplan)

Шаги 1-3 те же. Шаги 4-5 пропускаются: на каждую улику сразу заводится задание
на рецепт. Дальше 6-10 без изменений. Это абляция — показывает вклад
планирования.

### ApiGuideGenerator (конфиг gen_api)

Шаги 1-2 те же. Улики и планирование не используются. Вместо них **код**
отбирает 152 API: внутри каждой библиотеки сортировка по признаку «есть
похожий сосед», затем по частоте; равная квота на библиотеку; нижний порог 20
употреблений. Одно задание на API. Директивные задания те же 48. Шаги 7-10 без
изменений.

### Что генерирует модель, а что решает код

- Модель: план (только в gen_plan) и текст документов.
- Код: какие API существуют и как часто, какие темы вообще возможны, квоты по
  библиотекам, вся валидация, починка, дедупликация и материализация.

## Направления к обсуждению после exp18 (25.08.2026)

Три эксперимента подряд метрика не двигается. Konstantin предлагает сменить сам
предмет генерации. НИЧЕГО ЕЩЁ НЕ РЕШЕНО — три пункта ниже вынесены на
обсуждение вместе с замечаниями по каждому.

**1. Предложение: генерировать только поведенческие инструкции.** Инструкция не привязана ни
к библиотеке, ни к функции. Примеры формулировок (условные, окончательные
должны выводиться из типов задач и типовых ошибок):
«Если задача предполагает написать кусок кода — пиши только кусок, остальные
части переписывать запрещено»; «Не пиши result, если этого не требует задача».

**2. Предложение: кода в синтетике нет.** Строки кода допустимы только как few-shot —
подставляются, а не генерируются. Мотив: модель не фронтирная, на редких
функциях выдумывает. Подтверждено в exp17/exp18: `scipy.special.ccdf`,
`scipy.stats.ttest_onesamp` не существуют, выдуманное «устаревание» у
`torch .parameters()` — всё это попало в базу как исполнимый код.

**3. Предложение: если инструкция всё же про конкретную функцию** — функция берётся из
ОТДЕЛЬНОГО файла-словаря: библиотека → список её основных функций. Словарь
подставляется в запрос итеративно, плейсхолдером. Модель никогда не выбирает
сама, о чём писать. Файл отдельный ради масштабируемости: заменил словарь —
метод работает на другой предметной области.

**4. Замечание Konstantin: few-shot в нынешнем виде бесполезен для базы знаний.** Сейчас примеры
идут в запрос к генератору и влияют только на форму текста. В саму базу знаний
они не попадают. Konstantin: примеры кода имеет смысл класть в базу знаний как
есть, а не пересказывать их моделью.

### Замечания к предложениям (замеры, а не мнение) — на обсуждение

- Класс поведенческих инструкций — единственный с измеренным эффектом:
  +11.6 пп против +1.0 пп у рецептов с кодом. Ставка Konstantin совпадает с
  данными.
- Но такие инструкции плохо НАХОДЯТСЯ поиском: у ручных инструкций схожесть с
  текстами задач 0.175 против 0.314 у рецептов, и до контекста они доезжают
  примерно в 15% задач. Отсюда следствие: если инструкций будет два десятка и
  они не привязаны к теме, полагаться на поиск нельзя — их надо вставлять в
  подсказку принудительно. Это ровно тот «зарезервированный слот», который был
  отложен в exp17 и до сих пор не проверен.
- Ограничение сверху: ручная база содержит 17 таких инструкций. Сколько их
  вообще бывает — открытый вопрос; список должен выводиться из разбора ошибок
  (`results/error_analysis_exp8/`), а не сочиняться моделью.
