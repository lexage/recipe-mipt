# Задача: генератор правил для системного промпта солвера

## Контекст

В exp16 сравнили два канала доставки форматных правил: через RAG правила дали
+2.00 п.п., через системный промпт солвера — +5.90 п.п. Сейчас этот текст
захардкожен строкой в YAML
(`test_configs_experimental_16/e3_prompt_channel/e3_guide_in_prompt.yaml`), а
исходные 17 документов `guide_*` писал внешний агент по логам ответов и
эталонным решениям DS-1000.

Нужен метод, который **генерирует** эти правила: наше знание о проблемах
задаётся как список проблем в коде, а формулировки правил пишет LLM. Текста
правил в репозитории быть не должно.

## Что реализовать

### 1. `src/generation/prompt_rules.py` — компонент `PromptRuleGenerator`

Наследник `Block` (как `Generator`, но документы не возвращает). Публичный метод
`rules() -> str` — готовый блок правил для подстановки в системный промпт.

### 2. Список проблем — константа `PROBLEMS` в этом же модуле

17 записей, каждая — словарь с полями:

- `key` — короткий идентификатор;
- `symptom` — как выглядит неправильный ответ модели;
- `why` — почему это ломает проверку исполнением;
- `fix` — что отвечающий должен делать вместо этого.

Поля заполняются описанием **проблемы**, а не готовой формулировкой правила.
Темы (ровно 17):

1. повтор строк `import` из условия;
2. пересоздание входных переменных (`a`, `df`, `x`, `X`, `t`) значениями из
   примера;
3. повторный вызов генератора случайных данных или пересев seed;
4. вызов `load_data()` — это плейсхолдер, функции с таким именем не существует;
5. ответ положен не в ту переменную, которую просит задача;
6. `print()` вместо присваивания;
7. запрошено несколько выходных значений, присвоено одно;
8. задача просит изменить `df`, результат оставлен в новой переменной;
9. незаконченный `def f(...):` — нужно только тело с отступом и `return`, без
   повтора заголовка и без вызова;
10. обёртки в ответе: markdown-ограждения, XML-теги, проза до или после кода;
11. размеры и индексы взяты числами из примера вместо `len()`, `.shape`,
    `.columns`;
12. лишний `reset_index()`;
13. `.values` / `.to_numpy()` там, где ожидается DataFrame или Series;
14. лишние `astype`, сортировка, округление «для красоты»;
15. matplotlib: фигура уже создана, нужно только дополнять, `plt.show()` не
    нужен;
16. scipy: подмодуль надо вызывать так, как он импортирован в setup;
17. TensorFlow: код TF2 eager, без `Session` и `placeholder`.

Каждое описание — развёрнутое, 3–6 строк, с примером симптома. Это единственное
место, где живёт наше знание.

### 3. Промпт генератора — в коде модуля, не в YAML

Структура промпта:

- роль: пишешь системный промпт для модели, которая дописывает пропущенный код в
  уже исполненный фрагмент;
- условия задачи: setup исполнен, ответ вставляется в тот же namespace,
  проверяется исполнением на скрытых входах;
- описание одной проблемы (режим `per_problem`) или всех (режим `batch`);
- требования к формату вывода: одно правило, императив, одна-две строки, без
  названий библиотек в общих пунктах, без упоминания бенчмарка и его маркеров,
  без пояснений вокруг.

### 4. Два режима, оба рабочие, дефолт `per_problem`

**`per_problem`** — один вызов LLM на проблему, по списку. В промпт каждого
следующего вызова передаются уже принятые правила с двумя требованиями: не
дублировать и не противоречить. Если проблема уже покрыта принятым правилом,
модель отвечает `COVERED`, и пункт пропускается.

**`batch`** — один вызов со всеми 17 описаниями, на выходе список не более
`n_rules` пунктов, родственные темы модель объединяет сама.

Дедупликация — только этими двумя механизмами, без эмбеддингов и кластеризации.

### 5. Сборка и кэш

Собрать принятые правила в нумерованный список. Если он превышает
`max_prompt_tokens` (дефолт 600), писать предупреждение в лог. Финальный текст и
все промежуточные ответы сохранять в `rules_path` (jsonl: `key`, промпт, ответ,
принято или `COVERED`, модель, seed). При повторном запуске, если файл есть и
`rebuild: False`, брать текст из него — бенч должен перезапускаться на том же
тексте.

### 6. Подстановка в системный промпт

В `src/pipelines/templates/simple_pipeline.py` добавить необязательный параметр
`rule_writer: PromptRuleGenerator = None`. Если задан, после сборки индекса и до
прогона:

```
agent.system_prompt = agent.system_prompt.rstrip() + "\n\n" + rule_writer.rules()
```

Первую фразу системного промпта (про `<code>`-теги) не трогать: от неё зависит
парсинг ответа. Без параметра поведение пайплайна не меняется.

### 7. Регистрация и логирование

- `src/pipelines/constants.py`:
  `PROMPT_RULE_GENERATOR = "src.generation.prompt_rules.PromptRuleGenerator"`.
- `run_ds1000.py`: сохранять в папку результатов `system_prompt_used.txt` с
  итоговым текстом.

## Параметры компонента

`url`, `model_name`, `mode` (`per_problem` / `batch`), `n_rules` (для `batch`,
дефолт 12), `max_prompt_tokens` (600), `temperature` (0.3), `seed`,
`rules_path`, `rebuild`.

## Чего делать нельзя

- Копировать формулировки из документов `guide_*` или из
  `e3_guide_in_prompt.yaml`. Сгенерированный текст не должен дословно совпадать
  с ними.
- Читать DS-1000: ни `ds1000.jsonl.gz`, ни `answers.jsonl`, ни `results.csv`, ни
  эталонные решения.
- Менять корпус, ретривер, ассемблер, чанкер и параметры солвера кроме
  `system_prompt`.
- Добавлять стадии, которых нет в этом задании: самодиагностику, генерацию
  задач, эмбеддинги, оптимизацию промптов.

## Конфиги

Четыре конфига, отличаются только системным промптом. Корпус —
`data/docs_database_examples.db`, остальные компоненты одинаковые.

| Конфиг | Системный промпт |
|---|---|
| `r0_pure` | дефолтный, без правил |
| `r1_rules_per_problem` | правила от генератора, режим `per_problem` |
| `r2_rules_batch` | правила от генератора, режим `batch` |
| `r3_rules_manual` | захардкоженный текст из `e3_guide_in_prompt.yaml` |

`r3` нужен как потолок: без него не отличить «сгенерированные правила слабее
рукописных» от «канал промпта сам по себе что-то даёт».

## Порядок работы

1. Реализовать компонент, прогнать генерацию правил трижды с разными seed,
   **без бенчмарка**. Показать три текста заказчику до того, как занимать GPU.
2. Смоук: один конфиг, `-l 150`, проверить, что промпт доезжает до солвера и
   результаты пишутся.
3. Четыре полных прогона по 1000 задач с `--log-chunks`, последовательно.

## Критерии приёмки

- В коде нет готовых формулировок правил, только описания проблем.
- В дампе видно соответствие «правило → проблема», все 17 тем либо покрыты
  правилом, либо помечены `COVERED` со ссылкой на покрывающее правило.
- Повторный запуск с существующим `rules_path` даёт побайтно тот же системный
  промпт.
- Итоговый блок укладывается в бюджет токенов и не содержит дублирующихся по
  смыслу пунктов.
- В папке каждого прогона лежит `system_prompt_used.txt`.
