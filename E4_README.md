# Эксперимент E4 — несмещённая оценка прироста

## Зачем он нужен

Все остальные прогоны exp16 меряются на тех же 1000 задачах, по разбору ошибок
на которых корпус и строился. Агент-аугментатор получил логи всех 1000 ответов
baseline вместе с эталонными решениями, после чего дописал в БД 197 документов.
Даже если бы он ни разу не скопировал условие задачи дословно, темы этих
документов выбраны по распределению ошибок на тесте — а это методологически то
же самое, что подбирать гиперпараметры по тестовой выборке.

Аблации из E1 и E2 показывают, откуда взялся прирост, но снять смещение они не
могут: они выполняются на том же заражённом сете. Прямая утечка меряется —
удаление 58 документов T1+T2 стоит 4.2 п.п. из 10.15, то есть 41% прироста.
Селекционная утечка в оставшихся 139 документах T3 не меряется никак.

E4 — единственный способ получить число, которое можно показывать: агент видит
только часть задач, оценка идёт на остальных.

## Схема

```
1000 задач ds1000
   ├── 300 train  → агент разбирает ошибки, строит корпус
   └── 700 eval   → на них меряем, агент их не видел
```

Точки отсчёта уже посчитаны на тех же 700 задачах из готовых прогонов, заново
их гонять не надо:

| | PASS@1 на 700 held-out | Δ |
|---|---|---|
| `e0_baseline` | 43.79 | — |
| `e0_aug_full` | 55.07 | +11.29 |
| `e4_aug_train_only` | ? | ? |

Разность последней строки с первой и есть искомое число.

## Подготовка (уже выполнена)

```bash
python db_scripts/run_exp16_e4.py
```

Создал `data/exp16/split.json` — 300 train / 700 eval, seed 7.

```bash
python db_scripts/make_e4_agent_dossier.py \
    --answers     results/e0_baseline/<run>/answers.jsonl \
    --results-csv results/e0_baseline/<run>/results.csv
```

Создал `data/exp16/e4_agent_dossier.jsonl` — 300 записей, 415 КБ. По каждой
train-задаче: `problem_id`, `library`, `perturbation_type`, `prompt`,
`reference_code`, `model_code`, `passed`. Из 300 train-задач baseline провалил
166.

Почему понадобился отдельный файл, а не просто нарезанный `answers.jsonl`:
последний содержит только сгенерированный код и метаданные, без формулировок и
эталонов. Агенту пришлось бы искать их в `ds1000.jsonl.gz`, где лежат все 1000
задач вместе с held-out половиной. Досье закрывает эту дыру: в нём есть всё
нужное для разбора ошибок и нет ни одной held-out задачи.

Поле `code_context` (код чекера) в досье намеренно не включено. В первом проходе
агент выдал 28 документов, объясняющих, как грейдер сравнивает объекты — это
подгонка под функцию сравнения, а не под задачу, и повторять её незачем.

## Ручной шаг: перегенерация корпуса

Это единственная часть, которую нельзя запустить командой — нужен прогон агента.

**Входные данные — строго два файла:**

- `data/exp16/e4_agent_dossier.jsonl`
- `data/docs_database_examples.db` (исходный корпус, немодифицированный)

**Категорически нельзя давать агенту:**

- `data/ds1000/ds1000.jsonl.gz` — там все 1000 задач
- папку `results/` — там ответы по всем задачам
- `data/exp16/split.json` — по нему восстанавливаются id held-out
- уже готовый `docs_database_examples_aug.db` — он построен по всей тысяче
- любой пересказ того, как модель справилась с остальными 700

Одного просочившегося списка достаточно, чтобы эксперимент снова ничего не
измерял.

**Выход:** `data/exp16/docs_aug_train_only.db`

**Промпт** — исходный, адаптированный под 300 задач и один файл:

```
Привет! Смотри, у тебя есть файл data/exp16/e4_agent_dossier.jsonl — это разбор
работы агента на 300 задачах. В каждой записи: формулировка задачи (prompt),
правильный ответ (reference_code), ответ агента (model_code) и вердикт (passed).
166 из 300 задач агент решил неверно.

ВАЖНО: этот файл — единственный источник информации о задачах. Не открывай
датасет ds1000, папку results и никакие другие файлы с задачами. Работай только
с тем, что дано.

1. Первым делом отсмотри каждую ошибку: сравни правильный ответ и ответ агента.
   Нужно докопаться до сути. На основе анализа всех 300 ответов найди группы, в
   которые можно объединить ошибки по общим признакам. Нужно как-то
   классифицировать ошибки, потому что вероятно будет много однотипных, которые
   повторяются в разных запросах.
2. Далее нужно подумать, как расширив db дополнительными примерами можно было бы
   улучшить качество ответов. Это могут быть дополнительные описания, инструкции,
   как правильно решать некоторые типы задач, какие-то промпты, также могут быть
   добавлены в db. Помни, элементы базы данных будут векторизоваться и станут
   основой для RAG. Поэтому также необходимо подумать, как бы получше их записать
   так, чтобы они хорошо ретривились на задачах.
   ОЧЕНЬ ВАЖНО: запрещено добавлять что-то из тестового датасета в БД, нельзя
   добавлять правильные ответы, нельзя добавлять вопросы из датасета, нельзя
   копировать имена колонок, переменных и строковые литералы из формулировок
   задач.
3. Хочу от тебя получить подробное описание по первым двум пунктам: классификация
   ошибок, гипотезы их преодоления (помни, преодолеваем исключительно увеличением
   RAG, ничего другого не меняем, все промпты помещаем в RAG), а также идеи по
   формированию новой БД.
4. После этого мы должны обсудить гипотезы. И после этого твоя задача создать
   новый файл db — ОЧЕНЬ ВАЖНО, ты его делаешь на основе старого, ты берёшь его
   как есть, не переписываешь его элементы и не удаляешь ничего, ты просто
   добавляешь новые элементы в таблицы.

Исходная БД: data/docs_database_examples.db
Результат сохрани в: data/exp16/docs_aug_train_only.db
```

Отличие от промпта первого прохода одно: в пункт 2 добавлен явный запрет
копировать имена колонок и строковые литералы. В первом проходе формулировка
«нельзя добавлять вопросы из датасета» была соблюдена буквально, но 30
документов всё равно унесли из условий `celltype`, `Weight (kg)`,
`Pearson Correlation Coefficient`, `time_days` и другие.

Если нужна проверка переносимости **ровно той методики**, что дала +10.15, эту
строку следует убрать и оставить промпт дословно исходным. Тогда E4 померит
исходную процедуру на честной выборке. Рекомендуется добавленный вариант:
интереснее узнать, чего стоит корпус, построенный правильно.

## Оценка

```bash
python db_scripts/run_exp16_e4.py
```

Скрипт увидит появившийся корпус и продолжит сам. Порядок действий:

**Проверка корпуса.** Все ли 18 063 исходных документа на месте и не изменены —
агенту велено только дописывать. Сколько добавлено. Сколько добавленных
документов содержат строковые литералы, отсутствующие во всём исходном корпусе
(45 МБ documents + examples) — то же правило, по которому считался T1.

Последний пункт стоит посмотреть глазами. На train-задачах такие литералы
ожидаемы и сами по себе утечкой не являются: агент имел право видеть эти задачи.
Но если доля окажется сопоставима с первым проходом (30 из 197, то есть 15%),
это сигнал, что запрет снова не сработал и агент по-прежнему переписывает
условия дословно.

**Прогон.** Запускает `run_ds1000.py` с `--exclude-split data/exp16/split.json`,
что выбрасывает 300 train-задач и меряет на 700 оставшихся. Без этого флага
смысл теряется полностью.

**Сравнение.** Считает три строки на одних и тех же 700 задачах и разводит два
числа: прирост, измеренный на данных, по которым корпус строился, и прирост на
невиданных задачах.

## Как читать результат

Полученное число — **нижняя граница** переносимого прироста, и занижено оно по
двум причинам сразу.

Первая: train-срез втрое меньше, агент видел 166 провалов вместо примерно 560.
Корпус вышел беднее не только за счёт убранной утечки, но и просто потому, что
материала было меньше.

Вторая: часть эффекта исходной аугментации держится на форматных инструкциях
(`guide_*`) и миграционных заметках (`migr_*`), которые от размера выборки
зависят слабо. Их агент, скорее всего, воспроизведёт и на 300 задачах.

Развести эти два эффекта можно контрольным прогоном: сгенерировать корпус по 300
**случайным** задачам, взятым из тех же train-id, и померить на тех же 700.
Разница с E4 покажет чистый вклад размера выборки. Но это ещё одна перегенерация,
поэтому имеет смысл только если E4 даст пограничный результат.

Ожидание на основе уже полученных данных: 41% прироста снимается удалением 58
документов T1+T2, а остальное держится на 140 рецептах `howto_*`, каждый из
которых написан под конкретный наблюдённый провал. Логично ждать, что на
held-out прирост окажется заметно меньше одиннадцати пунктов. Но это ровно то,
что нужно измерить, а не угадать.

## Формулировка для отчёта

До получения E4 результат корректно описывается так:

> Корпус, построенный по разбору ошибок на ds1000, даёт +10.15 п.п. PASS@1 на
> том же ds1000. Из них не менее 4.2 п.п. приходится на документы, содержащие
> строковые литералы из условий задач или описания устройства чекера.

Формулировка «RAG-аугментация даёт +10.15 на ds1000» без E4 некорректна.
