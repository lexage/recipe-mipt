# Эксперимент 17 — воспроизводимая генерация синтетики

Exp16 разобрал ручную аугментацию на слагаемые. Exp17 пытается получить тот же
эффект генератором внутри пайплайна, без внешнего агента и без доступа к
DS-1000.

## Что взято из отчёта exp16

| Находка | Как учтена |
|---|---|
| `howto_*` дали +9.10 из +10.15 | Генератор пишет только рецепты |
| `migr_*` дали −0.20 | Миграционных заметок нет вообще |
| Правила через промпт +5.90, через RAG +2.00 | Правила в `system_prompt` солвера |
| Инлайн примеров даёт 0 и вредит | Корпус не трогаем |
| Покрытие ретрива решает всё | Заголовок — вопрос, как у запроса |
| 41% прироста — утечка T1+T2 | Темы из переписи API, DS-1000 не виден |

Последняя строка — главное отличие от ручной аугментации. Там темы выбирались по
наблюдённым провалам на тесте; здесь — по тому, о чём корпус вообще говорит.
Утечка T1 невозможна конструктивно, а не по инструкции.

## Установка

Три файла кладутся в репозиторий, один патч применяется:

```
src/generation/howto_recipes.py     методы 1 и 2
src/generation/oracle_errors.py     метод 4
db_scripts/set_exp17_ports.py       установка портов
db_scripts/make_e4_agent_dossier.py обновлён: появился --all
git apply register_generators.patch регистрация в ComponentNames
```

## Порты

Модели поднимаются вручную, порты плавают. Перед каждым запуском:

```bash
python db_scripts/set_exp17_ports.py --gen 7115 --solver 7114 --embed 7216
python db_scripts/set_exp17_ports.py --show      # проверить
```

Генератор, солвер и эмбеддер — три независимых эндпоинта. Генераторный блок
помечен комментарием `# GEN_URL`, поэтому если генератор и солвер живут на одном
порту, они всё равно различимы. Можно менять по одному: `--gen 8001` тронет
только генератор.

Сменить модель генератора без правки yaml: `--gen-model Qwen/Qwen3-14B`.

## Методы

**Метод 1 — `m1_howto_qwen25`.** Перепись API по корпусу (документы + таблица
`examples`), топ по частоте с квотами по библиотекам пропорционально их доле,
один рецепт на API. Модель пишет из своей памяти, видя только имя API.

**Метод 2 — `m2_howto_ctx_qwen25`.** То же самое плюс `context_docs: 3` — в
промпт кладутся реальные пассажи корпуса, упоминающие этот API. Модели велено
использовать их для фактической точности (имена аргументов, типы возврата,
актуальное написание API), но переписывать своими словами и со своими данными.
Отличие от метода 1 ровно в одном параметре, так что разница между прогонами —
это чистый вклад заземления.

**Метод 3 — `m3_howto_qwen3_8b`, `m3_howto_ctx_qwen3_8b`.** Те же два метода на
Qwen3-8B. Солвер везде остаётся Qwen2.5-32B, меняется только генератор.
Ожидание: разрыв m2−m1 на слабой модели должен быть больше, чем на сильной —
чем меньше модель знает, тем полезнее заземление.

**Метод 4 — оракул.** Генератор получает условия, ответы солвера и эталонные
решения. Провалы группируются по библиотекам и подаются пачками по 6, а не по
одному: ручной проход выдал примерно один рецепт на один провал, что и есть та
форма, которая не обобщается. Пачка заставляет назвать общий паттерн.

## Порядок запуска

```bash
# 1. досье для оракула
python db_scripts/make_e4_agent_dossier.py --all \
    --answers     results/e0_baseline/<run>/answers.jsonl \
    --results-csv results/e0_baseline/<run>/results.csv \
    --out data/exp17/dossier_all1000.jsonl

# 2. порты
python db_scripts/set_exp17_ports.py --gen 7115 --solver 7114 --embed 7216

# 3. смоук на одном конфиге, прежде чем занимать ночь
python run_ds1000.py -c test_configs_experimental_17/m1_howto_qwen25.yaml \
    --log-chunks -l 150

# 4. остальные, по одному
python run_ds1000.py -c test_configs_experimental_17/m2_howto_ctx_qwen25.yaml --log-chunks
...

# оракул на train-300 — ТОЛЬКО так
python run_ds1000.py -c test_configs_experimental_17/m4_oracle_qwen25_train300.yaml \
    --log-chunks --exclude-split data/exp16/split.json
```

Тёплый старт индексов из exp16 здесь не применим: у каждого конфига свой набор
сгенерированных документов, и chunk id у них разные. Но базовая часть корпуса
одинакова, так что копия `data/vdb_exp16_base_rc_1000` в
`data/vdb_exp17_<slug>_rc_1000` сэкономит по 40 минут на конфиг:

```bash
for s in m1_q25 m1_q25_np m2_q25 m3_q3 m3_q3ctx m4_q25_all m4_q25_300 m4_q3_all; do
  cp -r data/vdb_exp16_base_rc_1000 data/vdb_exp17_${s}_rc_1000
done
```

## С чем сравнивать

Это важнее всего остального: **у конфигов разные точки отсчёта.**

| Конфиг | Контроль | Значение контроля |
|---|---|---|
| `m1_howto_qwen25_noprompt` | `e0_baseline` | 44.10 |
| все остальные с `system_prompt` | `e3_guide_in_prompt` | 50.00 |
| `m4_oracle_qwen25_train300` | baseline на held-out | 43.79 |
| ручная аугментация (ориентир) | — | 54.25 |

Правила формата дают +5.90 сами по себе, поэтому конфиг с ними, показавший
52.00, добавил к делу не +7.9, а +2.0. Сравнение с 44.10 завысит вклад
генератора почти втрое.

`m1_howto_qwen25_noprompt` нужен именно для проверки, складываются ли эффекты.
Если m1 без промпта даёт +4, а с промптом 50.00 → 54.00, эффекты аддитивны. Если
с промптом прирост схлопывается, значит рецепты чинят то же самое, что и
правила, и большая часть работы генератора избыточна.

## Как читать результаты

**Метод 1 против e3 (50.00).** Ожидание скромное: +2…+5. Потолок без прямой
утечки, измеренный в exp16, — это `minus_T1+T2` = 50.05, то есть +5.95 к
baseline. Рецепты из параметрической памяти вряд ли превзойдут документы,
написанные по разбору реальных провалов, даже очищенные.

**Метод 2 минус метод 1.** Если разница положительная — заземление работает и
метод стоит масштабировать. Если нулевая — генератор и так знал эти API, а
корпус ничего не добавил, и это тоже полезный ответ: значит узкое место не в
фактической точности рецептов, а в покрытии ретрива.

**Метод 3.** Разрыв между Qwen3-8B и Qwen2.5-32B при одинаковом методе
показывает, во что упирается качество. Если 8B почти догоняет 32B, генерацию
можно удешевить радикально.

**Метод 4 — только диагностика.** Число на 1000 задачах прямо сопоставимо с
ручными +10.15, но заражено ровно так же и в отчёт не идёт. Отвечает на один
вопрос: способен ли Qwen2.5 извлекать полезное из эталонных решений вообще.
Если оракул на 1000 даёт заметно меньше +10.15 — значит ручной прирост держался
на способностях внешней модели, а не на самой процедуре, и локальная
воспроизводимость упирается в генератор. Если сопоставимо — процедура
переносима, и вопрос только в честности выборки.

Версия на train-300 честна и сравнима с E4: та же выборка, другой автор корпуса.

## Аудит утечки

Для методов 1–3 утечка невозможна конструктивно, но проверить стоит — генератор
мог случайно совпасть с формулировками задач. Для оракула проверка обязательна:
ему явно запрещено копировать литералы, и надо знать, соблюдён ли запрет.

Дампы сгенерированных документов лежат в `results/gen_dumps/*.jsonl`. Прогнать
по ним то же правило, по которому в exp16 считался T1 (строковые литералы,
отсутствующие во всём исходном корпусе), — скрипт напишем, когда появятся дампы.
