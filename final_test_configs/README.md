# Финальный эксперимент — генератор правил для системного промпта

Самодостаточный эксперимент: в нём есть свой бейзлайн и наш метод, мерим
дельту PASS@1 относительно этого бейзлайна.

## Что за метод

Наше знание о том, как ответ модели ломается при проверке исполнением, лежит в
коде списком **проблем** — `PROBLEMS_GENERAL` и `PROBLEMS_SPECIFIC` в
`src/generation/prompt_rules.py`. Каждая запись описывает проблему (как выглядит
неправильный ответ / почему это ломает проверку / что делать вместо этого), а не
готовое правило.

Формулировки правил пишет LLM. Готового текста правил в репозитории нет: блок
собирается из ответов модели и дописывается к системному промпту солвера после
сборки индекса. Первая фраза системного промпта (контракт про теги `<code>`, от
которого зависит разбор ответа) не трогается.

## Пять конфигов

Все пять одинаковы во всём, кроме системного промпта солвера.

| Конфиг | Список проблем | Режим генерации |
|---|---|---|
| `c0_base` | — | правил нет, дефолтный системный промпт |
| `c1_general_per_problem` | общие формулировки | по одному вызову на проблему |
| `c2_general_batch` | общие формулировки | один вызов на все 17 |
| `c3_specific_per_problem` | конкретные формулировки | по одному вызову на проблему |
| `c4_specific_batch` | конкретные формулировки | один вызов на все 17 |

**Два списка проблем.** `general` описывает ситуации как свойства класса задач
(код дописывается в уже исполненное окружение, проверка идёт исполнением на
входах, которые подставляет проверяющий) — без имён переменных, без вызовов и
маркеров конкретного бенчмарка. `specific` описывает те же 17 ситуаций с
конкретными артефактами. Сравнение показывает, сколько стоит отказ от
конкретики.

**Два режима.** `per_problem` — один вызов на проблему, принятые правила
подаются в следующий вызов с требованием не повторяться и не противоречить;
если проблема уже покрыта, модель отвечает `COVERED: <номер>` и пункт
пропускается. `batch` — один вызов со всеми проблемами, модель сама объединяет
родственные и возвращает не больше `n_rules` правил, помечая, какие проблемы
каждое покрывает. Другой дедупликации нет — ни эмбеддингов, ни кластеризации.

## Порядок работы

Порты в конфигах зафиксированы: наша модель на 7217, эмбеддер — на 7216,
где уже работает постоянный сервис лаборатории с `Qwen/Qwen3-Embedding-4B`.
Менять конфиги не нужно.

**Пять прогонов, последовательно.** `-c` на папку берёт `*.yaml` по алфавиту,
то есть `c0` → `c4`; локальный qdrant держит блокировку на каталог индекса,
параллельно гонять нельзя. Правила пишутся на этапе сборки пайплайна, отдельного
шага для них не нужно.

```bash
python run_ds1000.py -c final_test_configs --log-chunks
```

Если нужно посмотреть тексты правил отдельно от прогона (например, несколько
seed подряд), это делает `db_scripts/write_rules.py` — ему нужен только поднятый
эндпоинт, ни индекса, ни корпуса:

```bash
python db_scripts/write_rules.py -c final_test_configs/c1_general_per_problem.yaml --seeds 7,17,42 --out-dir results/rule_dumps
```

## Запуск на кластере

Узел `ali117197`, лаборатория `prims`. Питон на самом узле 3.6, поэтому всё
крутится в контейнере с образом `asllm`.

Окружение — один раз. В образе нет `qdrant-client`, `chromadb`, `matplotlib` и
`tensorflow`; первые два нужны, чтобы вообще импортировался `LocalDB`, вторые
два — чтобы исполнялись задачи соответствующих семейств. Скрипт делает venv с
`--system-site-packages` в доме и ставит туда недостающее:

```bash
bash scripts/setup_runner_env.sh
```

Два сервиса, по карте на каждый, длинная очередь:

```bash
sbatch -p "$LAB_LONG" scripts/svc-qwen36-7217.sbatch
```

```bash
sbatch -p "$LAB_LONG" scripts/svc-embed-7216.sbatch
```

Прогон карт не занимает — это клиент к двум эндпоинтам плюс исполнение кода
задач на CPU, поэтому запускается прямо на узле:

```bash
bash scripts/run_final.sh
```

Скрипт сам проверяет, что оба порта отвечают и что корпус с датасетом на месте,
и гоняет пять конфигов подряд.

## Что остаётся в папке прогона

Кроме обычных `results.csv`, `summary.txt`, `runtime_stats.json`:

- `system_prompt_used.txt` — системный промпт ровно в том виде, в каком он
  дошёл до солвера;
- `prompts.json` — промпты самого генератора правил;
- `results/gen_dumps/rules_<конфиг>.jsonl` — каждый вызов: промпт, ответ,
  принято / `COVERED` / отклонено, модель и seed, а последней строкой —
  собранный текст.

При `rebuild: False` (так во всех конфигах) существующий дамп переиспользуется:
повторный прогон идёт на том же тексте побайтно. Чтобы переписать правила,
поставить `rebuild: True` или удалить файл.

## Модели

Солвер и генератор правил — одна модель на одном эндпоинте
(`Qwen3.6-35B-A3B`, поднимаем сами на 7217), эмбеддер — `Qwen3-Embedding-4B`
на 7216, тоже наш (постоянный сервис лаборатории на этом порту сняли). Режим
рассуждений
выключен и у солвера, и у генератора (`enable_thinking: False`): ответ солвера
разбирается как голый код и режется по `</code>`.

Модель поднимается под именем, совпадающим с путём к весам, — солвер берёт
идентификатор модели с эндпоинта и этим же идентификатором грузит токенайзер.

## Корпус и индекс

Корпус `data/docs_database_examples.db` не меняется ни одним конфигом, поэтому
индекс `data/vdb_final_rc_1000` один на все пять прогонов: первый строит,
остальные переиспользуют.
