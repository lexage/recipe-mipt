# Эксперимент 16 — разложение прироста от ручной аугментации

## Зачем

Агент-аугментатор получил логи всех 1000 ответов baseline и эталонные решения,
после чего дописал в БД 197 документов. Прирост есть, но он измерен на том же
тест-сете, по разбору ошибок на котором корпус и строился. Сейчас это не
результат «RAG-аугментация даёт +X на ds1000», а результат «корпус, собранный по
ошибкам на этом сете, даёт +X на нём».

Exp16 раскладывает эту дельту на слагаемые и добывает одно несмещённое число.

Разбиение 197 документов на группы (обе классификации считаются заново скриптом,
ничего не захардкожено):

| по функции | | по привязке к тесту | |
|---|---|---|---|
| `guide_*` | 17 | T1 — литералы из условий ds1000 | 30 |
| `migr_*` | 40 | T2 — подгонка под чекер | 28 |
| `howto_*` | 140 | T3 — выглядят generic | 139 |

## Подготовка данных

Один раз, из корня репозитория:

```bash
# 1. Производные корпуса: base, aug_full, only_*, minus_*, minus_t1, minus_t1_t2
python scripts/make_exp16_dbs.py \
    --base data/docs_database_examples.db \
    --aug  data/docs_database_examples_aug.db \
    --out  data/exp16

# 2. Корпуса для E6 — примеры материализованы в documents.content
python scripts/make_inlined_examples_db.py \
    --in data/exp16/docs_base.db --out data/exp16/docs_base_inlined.db
python scripts/make_inlined_examples_db.py \
    --in data/exp16/docs_aug_full.db --out data/exp16/docs_aug_inlined.db
```

Сначала стоит посмотреть классификацию без записи 12 копий по 100 МБ:

```bash
python scripts/make_exp16_dbs.py --base ... --aug ... --out ... --dry-run
```

Ожидаемый вывод: `by function: {'guide': 17, 'migr': 40, 'howto': 140}`,
`by coupling: {'T1': 30, 'T2': 28, 'T3': 139}`. Если числа разошлись — значит
на вход подали не те файлы. Полная роспись каждого документа с его группой и
найденными литералами пишется в `data/exp16/manifest.json`.

Все корпуса строятся из **augmented** файла удалением строк, поэтому нетронутая
часть побитово одинакова во всех вариантах: между прогонами меняется ровно то,
какие из 197 документов остались. `docs_base.db` при этом полностью совпадает
с исходным `docs_database_examples.db`, а `docs_aug_full.db` — с `_aug.db`.
Занимает ~1.2 ГБ на диске.

## Порядок запуска

**Шаг 1 — опорные точки.** Обязательно первыми: exp15 гонялся на AWQ-солвере,
здесь везде не-AWQ, поэтому все прошлые числа несравнимы напрямую.

```bash
python run_ds1000.py -c test_configs_experimental_16/e0_reference --log-chunks
```

**Шаг 2 — тёплый старт индексов.** Экономит ~10 полных проходов эмбеддера.

```bash
python scripts/warm_start_exp16_vdbs.py
```

Работает потому, что id чанка — это `{doc_id}_{i}`, он не зависит от того,
какие ещё документы лежат в корпусе, а адаптер пропускает уже проиндексированные
чанки. Каждый вариант доэмбеддит только свои ~200 документов вместо всех 60k.
На корпуса E6 не распространяется: там переписан `documents.content`, старые
векторы стали бы невалидными — скрипт их не трогает.

**Шаг 3 — остальные группы,** в порядке убывания ценности:

```bash
python run_ds1000.py -c test_configs_experimental_16/e3_prompt_channel   --log-chunks
python run_ds1000.py -c test_configs_experimental_16/e6_examples_inlined --log-chunks
python run_ds1000.py -c test_configs_experimental_16/e2_leak             --log-chunks
python run_ds1000.py -c test_configs_experimental_16/e1_ablation_only    --log-chunks
python run_ds1000.py -c test_configs_experimental_16/e1_ablation_minus   --log-chunks
```

`-c` принимает каталог и берёт `*.yaml` без рекурсии, поэтому подпапки
запускаются независимо, а `-c test_configs_experimental_16` не найдёт ничего.
Гонять последовательно: локальный qdrant держит файловую блокировку на каталог
индекса, параллельные прогоны по одному пути упадут.

Для смоука перед полным прогоном:

```bash
python run_ds1000.py -c test_configs_experimental_16/e0_reference \
    --log-chunks -l 150
```

`-l` берёт задачи равномерно по датасету, так что распределение по библиотекам
сохраняется. Но: на 150 задачах доверительный интервал PASS@1 около ±4 п.п., то
есть различить группы можно только если дельта крупная. Смоук нужен для проверки
работоспособности, выводы — по полным 1000.

`--log-chunks` обязателен везде: без `retrieved_chunks.jsonl` нельзя посчитать
E7 (бакетирование задач по похожести на ближайший новый документ) и вообще
проверить, ретривились ли добавленные документы.

## Что в папках

**`e0_reference`** — `e0_baseline` (исходный корпус) и `e0_aug_full` (все 197).
Их разность и есть та дельта, которую всё остальное раскладывает.

**`e3_prompt_channel`** — 17 `guide_*` доставлены системным промптом, корпус
исходный. Если прирост воспроизводится, победа была не в retrieval, и её надо
переносить в промпт, а не в базу. `e3_guide_in_prompt` — сжатые правила
(~480 токенов), `e3_guide_in_prompt_verbatim` — все 17 документов дословно
(~2.8k токенов на каждый вызов). Второй запускать, только если первый прироста
не дал: он снимает возражение «сжатие потеряло содержание», но стоит ~2.8M
лишних входных токенов на прогон. Партнёр по сравнению — `e1_only_guide`.

**`e6_examples_inlined`** — плейсхолдеры `<example_N>` заменены на код примеров
**до** чанкинга и эмбеддинга. Сейчас `merge_examples` делает подстановку только
на выдаче, когда чанк уже выбран, то есть эмбеддер видит прозу с дырками, а
ручные документы несут код инлайн — структурное преимущество безотносительно
содержания. `e6_base_inlined` сравнивать с `e0_baseline`, `e6_aug_inlined` — с
`e6_base_inlined` (выживает ли прирост, если дефект корпуса починен).

**`e2_leak`** — `minus_t1` (без 30 документов с литералами из условий) и
`minus_t1_t2` (ещё и без 28 объясняющих устройство чекера). Даёт **нижнюю
границу** утечки: селекционная утечка в 139 документах T3 остаётся, все темы всё
равно выбраны по ошибкам на тесте. Слабая просадка не означает «утечки не было».
Удалить T1 надо в любом случае, независимо от цены в метрике: имён колонок из
ds1000 в базе быть не должно.

**`e1_ablation_only` / `e1_ablation_minus`** — по одной группе и без одной
группы. Обе схемы нужны, потому что аблации **не аддитивны**: документы
конкурируют за 5 мест в контексте, и убрав группу мы освобождаем слоты, после
чего оставшиеся начинают ретривиться там, где раньше не попадали. Сумма трёх
одиночных дельт не сойдётся с общей, и величина расхождения сама по себе
измеряет, насколько эффект про содержание, а насколько про борьбу за контекст.

**`e4_split`** — опциональный и самый дорогой, но **единственное несмещённое
число**. Требует заново прогнать агента-аугментатора на логах только train-части:

```bash
python scripts/make_ds1000_split.py --n-train 300 --seed 7 \
    --out data/exp16/split.json \
    --filter-answers results/<baseline_run>/answers.jsonl \
    --filter-out data/exp16/answers_train_only.jsonl
```

Агенту отдать **только** `answers_train_only.jsonl` и тот же исходный
`docs_database_examples.db`, результат положить в
`data/exp16/docs_aug_train_only.db`. Затем:

```bash
python run_ds1000.py -c test_configs_experimental_16/e4_split \
    --log-chunks --exclude-split data/exp16/split.json
```

Без `--exclude-split` смысл теряется полностью — оценка снова окажется на
задачах, которые агент видел.

## Чего здесь нет

**E5 (перенос на другой бенчмарк).** В репозитории есть только harness ds1000;
`src/benchmarks/SWE-bench` — вендоренный апстрим, не подключённый к
`PipelineBuilder`. Нужен отдельный раннер, конфигом не решается.

**E7 (бакетирование по похожести).** Это анализ поверх `retrieved_chunks.jsonl`
и `manifest.json`, а не прогон. Считается после того, как отработают шаги выше.
