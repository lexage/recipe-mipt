
## GitHub Repo Code Extractor

- **Модуль**: [`github_repo_loader`](../../../src/utils/github_parser/github_repo_loader.py) (и связанные парсеры)
- **Цель**: Автоматический сбор датасета пар «задача - решение» из исходного кода и документации GitHub-репозиториев.

**ВНИМАНИЕ**: оптимизировано под `torchmetrics`, работоспособность на других репозиториях не гарантирована!

## Принцип работы

Система сканирует указанный в конфиге [`src\utils\github_parser\default_github_fetcher_config.yaml`](../../../src/utils/github_parser/default_github_fetcher_config.yaml) репозиторий, фильтрует файлы и извлекает примеры кода, очищая их от служебных символов. Основная идея - отделить описание задачи (теорию) из докстринга от кода примеров (решения).

Высокоуровнево:

1.  **Загрузка**: `TorchGitHubLoader` подключается к GitHub API, обходит дерево репозитория и скачивает содержимое файлов, фильтруя их по расширению (`.py`, `.md`, `.rst`) и черному списку паттернов из конфига (например, `test`, `pycache`).
2.  **Маршрутизация**: В зависимости от типа файла `DatasetBuilder` передает контент соответствующему парсеру:
    *   `.py` → **CSTCodeParser** (на базе `LibCST`);
    *   `.md` → **MarkdownParser** (Regex);
    *   `.rst` → **RSTParser** (Regex).
3.  **Парсинг и Извлечение**:
    *   Для Python: обход AST-дерева, поиск классов и функций. Анализ докстрингов на наличие секций `Examples` или REPL-блоков (`>>>`). Текст *до* примера становится "задачей" (теорией), код примера - "решением".
    *   Для Markdown/RST: поиск блоков кода (code fences) и doctest-блоков с помощью регулярных выражений. Текст перед блоком считается описанием задачи.
4.  **Очистка (Post-processing)**:
    *   Удаление символов REPL (`>>>`, `...`);
    *   Удаление служебных комментариев (`# doctest: ...`);
    *   Фильтрация слишком коротких строк (например, просто вызов переменной для print).
5.  **Агрегация**: Результат собирается в список объектов `ExtractedExample`.

## Параметры инициализации и запуск

Для работы требуется добавить в `.env` файл переменную `GITHUB_ACCESS_TOKEN` с персональным токеном GitHub.

Основные параметры конфигурации (`GitHubExampleFetcherConfig`):

-   `repo_for_analyzing`: целевой репозиторий (по умолчанию `Lightning-AI/torchmetrics`).
-   `specific_folder_for_analyzing`: путь к папке/файлу для точечного анализа. Если не задан, будет анализироваться весь репозиторий.
-   `allowed_file_extensions`: список расширений ( `.py`, `.md`, `.rst`).
-   `min_code_length_for_analyzing`: минимальная длина строки кода (по умолчанию 7), чтобы отсеять мусорные принты переменных.
-   `extract_examples_from_root_readme`: флаг парсинга корневого README.

**Логирование**:
Пишется в файл `github_repo_processor.log` (захардкожено в `main`), требуется поправить после настройки конфигурации всего проекта.

## Алгоритм парсинга

### 1. Обработка Python файлов (`CSTCodeParser`)
Использует библиотеку `LibCST` для надежного разбора синтаксиса.
1. Строит дерево модулей.
2. `DocstringProcessor` посещает узлы `ClassDef` и `FunctionDef`.
3. Если в докстринге найдены ключевые слова `Example` или символы `>>>`:
   - Докстринг разбивается на части.
   - Общее описание (args, returns) склеивается с описанием конкретного примера.
   - Извлекается код, очищается функцией `clean_code_lines_from_repl_symbols_and_doctest_comments`.

### 2. Обработка Markdown/RST (`MarkdownParser`, `RSTParser`)
1. Очистка файла от специфичного мусора (HTML-тегов, директив Sphinx типа `.. plot::`).
2. Поиск совпадений по паттернам блоков кода (например, ` ```python ... ``` ` или `.. code-block::`).
3. Извлечение текста *перед* найденным блоком в качестве описания задачи.
4. В корневом README реализована специфичная логика разбиения на секции по заголовкам (через `root_readme_target_sections`), чтобы игнорировать "мусорные" секции.

## Проблемы и замечания

В ходе разработки и тестирования на репозитории `torchmetrics` выявлены следующие проблемы и замечания:

### 1. Ограничения покрытия
Работоспособность метода протестирована на папках:
  - src/wrappers;
  - src/torchmetrics/text;
  - src/torchmetrics/nominal;
  - src/torchmetrics/multimodal.
  - корневой файл README.md (с фильтрацией секций).
  - docs/source/pages/plotting.rst.

### 2. Проблемы форматирования и чистоты данных
- **Doctest директивы**: Встречаются конструкции вида `# doctest: +NORMALIZE_WHITESPACE`. Реализована их очистка, но могут проскакивать редкие вариации.
- **Висячие переменные**: Код вида `best_acc` (просто имя переменной для вывода в консоль REPL) отсекается фильтром `min_code_length_for_analyzing = 7`. Следует, возможно, почистить это еще каким-то способом. 

### 3. Технические долги (TODO)
- Логирование захардкожено в файл, нужно изменить после появления общей конфигурации.
- Возможно, стоит дополнительно обработать файлы в папке examples и _samples. Текущий функционал тестировался и работает на папках внутри `src/...`.
- Стоит доработать текущий функционал обработки .rst файлов (UPD: сейчас они парсятся в целом адекватно, но некоторое деление примеров, которое получается после регулярок, я считаю логически не совсем корректным. Таких файлов немного - всего 5 (все лежат внутри папки `docs/source/pages/`), которые представляют наборы описание задачи+решение, поэтому проще и не очень вычислительно затратно будет прогнаться LLM).
- Проанализировать, как обрабатываются файлы формата .md (помимо корневого README), внести коррективы, если необходимо. UPD: из того, что я видела в репозитории, остальные больше информационные без нужных нам пар, но мб стоит точнее посмотреть.
- Я бы ввела дополнительную фильтрацию LLM-кой после процесса получения датасета для полной уверенности, что все корректно сделано. Место, куда, как мне кажется, нужно вставить фильтрацию, отмечено комментарием # TODO в модуле [`__main__.py`](../../../src/utils/github_parser/__main__.py), но это остается на желание человека, перенимающего эту задачу.

## Запуск
Запустить модуль можно командой `python -m src.utils.github_parser`.
